# 0025 — CI/CD (GitHub Actions mit portabler CI-Logik)

- **Status:** Accepted
- **Datum:** 2026-07-10
- **Bezug:** [Architekturziel 5](../foundation/07-architekturziele.md) (Reproduzierbarkeit);
  Qualitätsattribute QA6 (Testbarkeit), QA3 (Wartbarkeit), QA5 (Portabilität);
  Entscheidungsprinzipien P1 (boring & bewährt), P8 (Reversibilität), P10 (Automatisierung),
  P11 (TCO); [Leitprinzip 9](../foundation/03-leitprinzipien.md) (Souveränität);
  [Leitprinzip 4](../foundation/03-leitprinzipien.md) (Reproduzierbarkeit);
  Risiken [R9](../foundation/09-risiken.md) (Contributor-Reibung),
  [R10](../foundation/09-risiken.md) (Veraltung); nutzt
  [ADR-0023](0023-build-task-tooling.md) (pnpm/Nx-Targets) und trägt die Gates aus
  [ADR-0022](0022-web-plattform-baseline.md) und [ADR-0027](0027-security-baseline.md).

## Kontext und Problemstellung

OpenCivic braucht Continuous Integration/Delivery, die Tests, das a11y-Gate, die
Contract-Validierung und die Sicherheits-Gates automatisiert (P10; QA6). Das Repository liegt auf
GitHub ([ADR-0023](0023-build-task-tooling.md)), und dort sitzt auch die Contributor-Community —
ein Wechsel weg von GitHub würde die Beitragshürde erhöhen ([R9](../foundation/09-risiken.md)).
Gleichzeitig gilt der Souveränitätsanspruch ([Leitprinzip 9](../foundation/03-leitprinzipien.md)):
Die Plattform darf sich nicht so tief an einen proprietären CI-Anbieter binden, dass ein späterer
Wechsel unmöglich wird (P8). Die Frage ist nicht nur „welche CI", sondern **wie tief** wir uns an
sie koppeln.

## Betrachtete Optionen

- **Option A — GitHub Actions, tief integriert:** volle Nutzung des Marketplace und
  GitHub-spezifischer Features.
- **Option B — GitHub Actions als dünne Trigger-Schicht über portabler CI-Logik:** die eigentliche
  Logik in Skripten/Task-Targets, Actions nur als Auslöser.
- **Option C — selbstgehostetes Forgejo Actions / Woodpecker von Anfang an.**
- **Option D — Jenkins.**

## Entscheidung

**Option B — GitHub Actions als dünne Trigger-Schicht über portabler CI-Logik.**

Die eigentliche CI-Logik lebt in **portablen Task-Targets** (Nx-Targets aus
[ADR-0023](0023-build-task-tooling.md), gekapselt hinter Makefile-/Task-Targets), die lokal und in
jeder CI **identisch** laufen — `make ci` auf dem Laptop tut dasselbe wie im Workflow. GitHub
Actions ist nur der dünne Auslöser: Es checkt aus und ruft die Targets auf. Bewusst **kein Lock-in
in proprietäre Marketplace-Actions** — die Logik gehört ins Repo, nicht in eine Blackbox-Action.

Das macht die CI portabel: Eine Migration zu Forgejo Actions, Woodpecker oder GitLab CI bedeutet,
die dünne Trigger-Schicht neu zu schreiben, nicht die Build-Logik (P8; QA5;
[Leitprinzip 9](../foundation/03-leitprinzipien.md)). Zugleich bleibt die Community dort, wo sie ist
— pragmatisch auf GitHub ([R9](../foundation/09-risiken.md)).

**Reproduzierbarkeit als Regel:** Actions werden auf **gepinnte Commit-SHAs** festgelegt (nicht auf
bewegliche Tags — ein Tag kann still umgehängt werden), Tool-Versionen und Lockfiles sind gepinnt
(P1, P11; [Leitprinzip 4](../foundation/03-leitprinzipien.md)). So bleibt eine Pipeline über Jahre
nachvollziehbar und ist gegen Supply-Chain-Angriffe auf die CI selbst gehärtet (siehe
[ADR-0027](0027-security-baseline.md)).

## Konsequenzen

- **Positiv:** Pragmatischer Default ohne Reibung für Contributor (R9); CI-Logik lokal reproduzierbar
  (QA6); Anbieterwechsel bleibt realistisch möglich (P8, QA5); gepinnte, reproduzierbare Läufe (P1).
- **Negativ / Kosten (ehrlich benannt):** Die dünne Kapselung ist **mehr Disziplin** als die
  bequeme Vollnutzung des Marketplace — es ist verlockend, „mal eben" eine fertige Marketplace-Action
  zu nutzen; diese Grenze muss im Review aktiv gehalten werden. Manche Komfortfeatures (spezielle
  Integrationen) werden bewusst nicht genutzt.
- **Reversibilität (P8):** Hoch — genau der Zweck der Schichtung. Der Aufwand eines CI-Wechsels ist
  auf die Trigger-Schicht begrenzt.

## Vor- und Nachteile der Optionen

### Option A — GitHub Actions, tief integriert

- 👍 Maximale Bequemlichkeit: fertige Marketplace-Actions für fast alles, minimaler
  Schreibaufwand, schnellste Einrichtung — der ehrliche Komfortvorteil.
- 👎 Lock-in: Die CI-Logik verteilt sich auf proprietäre, versionsschwer nachvollziehbare Actions;
  ein Anbieterwechsel wird teuer, lokale Reproduktion schwierig — Spannung zu P8/QA5.

### Option B — Dünne Trigger-Schicht über portabler Logik *(gewählt)*

- 👍 Portabel, lokal reproduzierbar, anbieterunabhängig — Souveränität ohne Community-Reibung; die
  CI-Logik ist versioniert und review-fähig im Repo.
- 👎 Etwas mehr initialer Aufwand und fortlaufende Disziplin, dem Marketplace-Komfort zu
  widerstehen.

### Option C — Forgejo Actions / Woodpecker von Anfang an

- 👍 Maximale Souveränität von Tag eins — vollständig self-hosted, keinerlei Abhängigkeit von einem
  kommerziellen Anbieter; philosophisch der reinste Weg und der ehrlich stärkste Punkt gegen die
  getroffene Wahl.
- 👎 Höhere Betriebslast früh (CI-Runner selbst betreiben und warten), und die Community sitzt heute
  auf GitHub — das erzeugt Contributor-Reibung ([R9](../foundation/09-risiken.md)) in einer Phase,
  in der Beiträge wichtiger sind als maximale Betriebs-Souveränität. Die portable Logik hält diesen
  Weg jederzeit offen (P8).

### Option D — Jenkins

- 👍 Sehr mächtig, extrem verbreitet, self-hostbar, riesiges Plugin-Ökosystem.
- 👎 Hoher Wartungsaufwand, plugin-getriebenes Alt-Modell mit eigener Sicherheits- und
  Pflegelast — widerspricht P11 (TCO) und dem Boring-aber-schlank-Anspruch; für ein
  Freiwilligen-Projekt eine unverhältnismäßige Betriebsbürde (R10).
